# Upgrading to 1.6

Version 1.6 closes a writing store asynchronously, so that no `fsync` blocks the process anymore.

---

## `close()` completes asynchronously

`EventStore.close()` and `Storage.close()` of a writer return before everything is on disk. In the background, they sync everything written as configured with `syncInterval` or `syncOnFlush`, sync the changed indexes, and only then release the lock. Pass a callback, or for a `Storage` wait for `'closed'`, to know when that is done.

```js
// Before (1.5)
eventstore.close();
process.exit(0);

// After (1.6)
eventstore.close((error) => {
    process.exit(error ? 1 : 0);
});
```

- If the process exits before the callback, the lock stays behind and the next open repairs the store as after a crash. Without `syncInterval` or `syncOnFlush`, the data itself is safe as before, but the indexes may not be on disk.
- Opening the same storage again in the same process waits until the close is done, so `close()` followed by `new EventStore(...)` keeps working. The same `Storage` instance reopens right away and keeps its lock.
- If a sync fails, the callback gets the error. Without a callback, the storage emits `'error'`.
- Deleting the storage directory right after `close()` is safe: files that are gone are not synced anymore.

## `syncOnFlush` groups the flushes of one tick

`syncOnFlush: true` no longer calls `fsync` inside each flush. It starts a sync run right after the current tick, like `syncInterval` with an interval of 0, and acknowledges the commits after that run. Commits within one tick, or during a running sync, share one `fsync` per file. The durability guarantee is unchanged: a commit callback still fires only after its data was synced.
